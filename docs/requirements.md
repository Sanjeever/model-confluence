# 模汇（model-confluence）产品需求与设计

本文档维护产品边界、领域契约、架构约束和已接受的安全取舍，作为后续设计与开发的依据。首版于 2026-08-11 冻结；后续明确采用的能力和决策在对应章节维护，不与发布版本号逐次绑定。

正文的「必须」「禁止」及验收条目表达设计要求，不代表实现已经全部满足。冻结的规划能力集中在第 14 节；已确认的实现差距集中在第 17 节。当前实现行为以代码、schema 和相关测试为依据，运行步骤与配置默认值见 [运行与开发](operations.md)。

发生冲突时，区分过时的实现描述与仍有效的设计约束；实现缺口不能自动成为新契约，设计要求也不授权 Agent 顺手补齐功能。重大决策变化应在相关章节保留原因与适用边界，不必为局部实现另建 ADR 或维护一份重复的字段表。

## 1. 产品定义

模汇是一款面向个人私有部署的 AI 协议网关。它以单个 Go 可执行文件发布，内嵌 React 管理后台，使用外部 SQLite 文件持久化配置与日志，为 Codex、Claude Code 和 OpenAI Chat Completions 兼容工具提供统一入口。

首版只解决三件事：

- 用虚拟模型和上游密钥池统一管理多个 AI 供应商；
- 在 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 三种协议之间进行双向转换；
- 完整记录请求路由、转换、上游尝试、响应与延迟，提供单请求追踪界面。

协议能力必须配置到「真实模型候选的协议入口」一级：同一供应商的不同模型可能提供不同的协议或能力，仅在供应商一级配置会让路由错误地假设所有模型都能接收同一种请求。

客户端兼容范围是 HTTP 与 SSE 的文本、图片输入和工具核心循环，因此必须保留 Responses 入口；WebSocket 不在支持范围。客户端产品的额外能力不自动扩大网关契约。

## 2. 用户与部署边界

- 仅面向单管理员、个人私有实例，不实现用户、团队、租户和角色体系。
- 远程访问经 HTTPS 反向代理，TLS 由 Caddy、Nginx 等反向代理终止；应用自身只提供 HTTP，本机可直接使用 localhost。
- 本机部署默认仅绑定回环地址；远程访问通过反向代理，实际监听配置见运行与开发文档。
- 只有显式配置的可信代理 CIDR 才能提供可信的 `Forwarded` 或 `X-Forwarded-For` 信息；其他请求使用 TCP 对端地址。
- 二进制与容器发布目标由发布工作流维护，用户选择对应平台产物；运行不依赖 Node.js。
- 发布物只有一个可执行文件。运行时允许产生 SQLite、WAL 和必要的临时文件；前端资源和数据库迁移必须嵌入可执行文件。
- 不支持多个进程或多个实例共享同一个 SQLite 数据库，也不做横向扩容。

## 3. 名词与数据关系

### 3.1 访问密钥

网关签发给 Codex、Claude Code 和其他客户端使用的入站密钥。所有访问密钥权限相同，不配置模型白名单、供应商白名单、配额或速率限制。

访问密钥具有独立启停、可选过期时间和归档生命周期。最后使用信息用于管理观察，不构成权限或配额限制；字段与持久化定义见 [schema](../internal/store/migrations.go)。

三个生成端点均接受 `Authorization: Bearer <key>` 和 `x-api-key: <key>`。两种头同时存在且值不一致时拒绝请求。

### 3.2 供应商

供应商表示一组共享鉴权方式、上游密钥池和协议端点的 HTTP 服务。

供应商配置鉴权方式（Bearer、`x-api-key` 或自定义头）、静态头、各协议完整请求 URL、密钥池和额度耗尽错误码精确列表。

优先级属于虚拟模型的候选顺序，过期时间属于每一把上游密钥，不设供应商全局优先级、模型映射或过期时间。管理后台提供配置模板以减少手工录入，具体模板与端点以 [模板定义](../web/src/providerTemplates.ts) 为准；模板不代表实时验证或自动同步。

### 3.3 上游密钥

每把上游密钥有独立的管理员启停、过期时间和运行状态。鉴权失效、额度耗尽与限流状态不能覆盖管理员意图；管理员可以重置运行状态，但不会改变密钥原文或启停状态。

密钥池按最久未使用轮询，时间相同保持池内顺序；明确的鉴权、限流或额度错误才在同候选内切换下一把。此规则用于分散调用，而非配额保证或并发公平性承诺；使用时间的维护以 [路由实现](../internal/store/routing.go) 为准。

### 3.4 虚拟模型与候选

客户端只请求虚拟模型名。每个虚拟模型包含一个有序候选列表，每个候选指向一个供应商和真实模型名。

候选字段：

- 供应商；
- 真实模型名；
- 管理员状态；
- 候选顺序；
- 默认最大输出 Token；
- 最大输出 Token 上限；
- 一个有序的协议入口列表。

候选协议入口字段：

- 协议类型：Chat Completions、Responses 或 Messages；
- 后备顺序；
- 是否支持流式；
- 是否支持工具调用；
- 是否支持并行工具调用；
- 支持的推理强度集合；
- 是否支持在 Chat 流中返回 usage。

路由先按当前请求需要的能力过滤不合格候选，再按候选顺序选择。候选优先级高于“避免转换”：先选择最高优先级的合格候选，再在该候选内部优先使用与客户端相同的协议；没有同协议入口时，使用候选配置的协议后备顺序。

## 4. 对外 API

所有模型 API 都需要访问密钥鉴权。

| 方法 | 路径 | 客户端协议 | 首版支持 |
| --- | --- | --- | --- |
| POST | `/v1/chat/completions` | OpenAI Chat Completions | 流式与非流式 |
| POST | `/v1/responses` | OpenAI Responses | HTTP 与 SSE，不支持 WebSocket |
| POST | `/v1/messages` | Anthropic Messages | 流式与非流式 |
| GET | `/v1/models` | OpenAI 兼容模型列表 | 返回已启用虚拟模型 |
| GET | `/healthz` | 最小健康检查 | 无需鉴权 |

`/healthz` 只检查进程已经启动且 SQLite 可访问，不探测上游，也不返回供应商配置。

模型列表用于展示管理员启用且有已配置候选的虚拟模型，不以实时健康筛选，避免临时限流或故障冷却导致列表闪烁。当前列表查询与候选存在性要求的差距见第 17 节。

请求中的模型名必须精确匹配虚拟模型，不存在时明确报错，不使用默认模型或原样透传兜底。

## 5. 协议路由矩阵

| 客户端端点 | 客户端协议 | 上游协议 | 行为 |
| --- | --- | --- | --- |
| `/v1/chat/completions` | Chat Completions | Chat Completions | 治理式透传 |
| `/v1/chat/completions` | Chat Completions | Responses | 双向转换 |
| `/v1/chat/completions` | Chat Completions | Messages | 双向转换 |
| `/v1/responses` | Responses | Responses | 治理式透传 |
| `/v1/responses` | Responses | Chat Completions | 双向转换 |
| `/v1/responses` | Responses | Messages | 双向转换 |
| `/v1/messages` | Messages | Messages | 治理式透传 |
| `/v1/messages` | Messages | Chat Completions | 双向转换 |
| `/v1/messages` | Messages | Responses | 双向转换 |

治理式透传仍会替换上游鉴权、将虚拟模型名改为真实模型名、合并供应商静态头、采集 usage、记录日志，并在客户端响应中把模型名改回虚拟模型名。除此之外，请求体、响应状态、响应体和流式事件尽量保持上游原样。

## 6. 转换能力边界

### 6.1 必须支持

- 流式与非流式文本；
- 多轮 user/assistant 消息；
- 对话开头的 system/developer/instructions；
- 客户端执行型工具定义、工具调用与工具结果；
- 并行工具调用；
- Responses 的 `function`、`custom`、`shell` 和 `apply_patch` 客户端执行型工具；
- 最大输出 Token；
- `temperature`、`top_p`、停止序列等三协议有明确公共语义的参数；
- `auto`、`none`、`required` 和指定工具等可等价表达的工具选择；
- 停止原因；
- usage 与缓存 Token；
- 可表达的明文 reasoning/thinking 输出，区分输出展示与历史往返；
- `low`、`medium`、`high`、`xhigh` 推理强度的等值映射；
- 文本增量、工具调用增量、结束和错误事件的 SSE 转换。

Responses 的 `custom`、`shell` 和 `apply_patch` 在目标协议中规范化为具名客户端工具，响应时还原为客户端需要的类型。

OpenAI 的 `minimal` 和 Anthropic 的 `max` 不是公共档位。目标入口不支持时必须在调用上游前拒绝，不做就近映射。使用记录同时保存客户端请求值和实际发送值。

OpenAI 的 system/developer 与 Anthropic 顶层 system 不完全等价。首版只允许对话开头的高优先级指令，按原顺序折叠到目标协议的最高优先级指令区；对话中途出现 system/developer 指令时拒绝。

当客户端没有提供最大输出 Token，而目标 Messages 入口要求该值时，使用候选配置的默认值。客户端值超过候选上限时，应在调用上游前拒绝；当前执行范围见第 17 节。

### 6.2 图片输入与明确不支持跨协议转换

跨协议请求支持图片输入，三种协议中的图片 URL、data URL 和 base64 图片在规范模型中统一表示，并保留图片与文本的顺序。跨协议不支持供应商私有的 `file_id` 图片引用。

Chat Completions 与 Responses 的 `detail` 支持 `auto`、`low`、`high`；Messages 没有等价字段。转换到 Messages 时，未设置或显式设置为 `auto` 的 detail 可以省略，`low` 和 `high` 必须在上游调用前明确拒绝，不能静默丢弃。

以下能力明确不支持跨协议转换：

- 音频、视频和文件输入；
- 结构化输出和 JSON Schema 响应格式；
- provider-hosted web search、file search、computer use、code interpreter、image generation 和远程 MCP；
- Anthropic thinking/signature、Responses reasoning/encrypted content 和供应商私有 reasoning_content 的跨协议往返；
- `previous_response_id`、conversation、background 和其他服务端会话状态；
- Responses WebSocket；
- 服务端 compaction、prompt template、Batch、Files 等非生成端点。

上述协议字段限制针对跨协议转换；同协议生成请求尽量保留未知字段。网关只注册已列出的 HTTP 入口，同协议透传不意味着提供 WebSocket、Batch、Files 等额外端点。

Responses 转换保持无状态，避免让供应商会话标识变成网关隐式状态。`store: false` 可以接受；`previous_response_id`、conversation、background 或要求网关保存会话的请求必须明确拒绝。日志不能充当 Responses 会话存储。

### 6.3 严格转换与两个例外

跨协议只接受明确支持的字段。任何非空未知字段或不支持字段都在调用上游前返回 `400`，错误中列出 JSON 路径；值为 `null` 视为未设置。同协议透传未知字段。

只有以下两类非语义信息允许在跨协议时丢弃，并且必须在需求和日志中可见：

- 源协议专用版本/Beta 请求头。同协议透传，跨协议记录但不转发；不能仅因存在 `anthropic-beta` 等头就拒绝请求。
- 缓存性能提示，例如 Anthropic `cache_control` 与 OpenAI `prompt_cache_key`。同协议透传，跨协议记录但不尝试近似映射，最终以真实上游 usage 为准。

思考内容不属于可丢弃例外。明文推理输出可以用于展示，但不证明历史回传等价；客户端显式要求目标协议无法提供的 thinking/reasoning 内容时必须在调用上游前拒绝。signature、redacted_thinking 和 encrypted content 不得伪造为其他协议字段。当前兼容行为与设计差距见第 17 节。

## 7. 转换架构约束

受限中间模型让跨协议映射具有可审查的公共语义，避免把未知字段当作可等价能力。治理式透传用于保留同协议的供应商扩展；二者不能混用来绕过能力校验。

- 同协议请求绕过中间模型，执行治理式透传。
- 跨协议请求解析为一个受限的规范中间模型，再编码到目标协议。
- 流式响应解析为规范事件，再编码为客户端事件。
- 转换器不得用 `map[string]any` 静默搬运未知字段；未知字段检查必须发生在上游调用前。
- 工具调用 ID 使用网关生成的跨协议安全 ID，保证同一完整上下文内的工具调用和结果能无状态对应。
- 客户端响应中的 `model` 始终是虚拟模型名；真实模型仅出现在管理日志。
- 网关为每个入站请求生成独立 `request_id`，通过响应头返回并贯穿全部 attempts。
- 同协议保留上游对象 ID；跨协议生成符合目标形状的对象 ID，同时在日志保存源 ID 和目标 ID。

## 8. 流式提交与取消

流式提交是重放安全边界：客户端一旦看到有效内容，再接入第二个响应会破坏文本与工具调用的一致性。以下为设计要求；当前 HTTP 提交、元事件与心跳的差异见第 17 节。

- 为保留首内容前的故障切换能力，网关缓冲响应头和 created/start 等无内容事件。
- 收到首个可验证的文本或工具调用增量时，一次性写出已缓冲事件；该时刻称为流式提交点。
- 流式提交后禁止切换密钥、候选或拼接第二个上游响应。
- 客户端断开后立即取消上游，不再故障切换，保存已获得的部分载荷并将请求标记为 `cancelled`。
- 后台不提供取消按钮，也不实时尾随响应正文。进行中记录通过轮询显示状态、当前候选和已知延迟；完整载荷在 attempt 结束后展示。

## 9. 上游失败、密钥池与故障切换

自动重放只允许发生在流式提交点之前，并且只针对明确可切换的错误。

| 情况 | 当前密钥状态 | 当前请求行为 |
| --- | --- | --- |
| `401` | 持久标记鉴权失效 | 尝试下一密钥 |
| `403` | 不改变长期状态 | 尝试下一密钥，无可用密钥时进入下一候选 |
| `402` 且结构化错误码命中供应商额度耗尽列表 | 标记额度耗尽 | 尝试下一密钥 |
| 其他 `402` | 不改变长期状态 | 尝试下一密钥 |
| `429` 且结构化错误码命中供应商额度耗尽列表 | 标记额度耗尽 | 尝试下一密钥 |
| 其他 `429` | 按 `Retry-After`，缺失时冷却 60 秒 | 尝试下一密钥 |
| 连接失败、响应头超时、流空闲超时、`5xx` | 不淘汰密钥 | 尝试下一候选 |
| 普通请求参数 `4xx` | 不改变 | 按客户端协议直接返回 |
| 结构化 `model_not_found` / `model_not_supported` | 候选标记配置错误 | 尝试下一候选，直到管理员重置 |
| `2xx` 但 JSON/SSE 不符合声明协议 | 候选故障 | 提交前切下一候选；提交后发流错误并结束 |

额度耗尽以结构化错误码的精确值判定，不使用错误文案、子串或正则，避免误禁用密钥。设计要求有可靠恢复信号时可自动恢复；没有信号时保持耗尽，直到管理员重置。当前额度恢复能力与错误码读取范围见第 17 节。

候选的瞬时连接故障、超时和服务端故障通过内存冷却与单次探测隔离，进程重启后清空；重试使用有上限的指数退避，避免立即反复冲击上游。阈值与退避时长以 [网关实现](../internal/gateway/handler.go) 和 [相关测试](../internal/gateway/handler_test.go) 为准。

鉴权失效、额度耗尽、密钥过期时间和候选配置错误需要持久化，防止重启绕过长期不可用状态。管理员状态与运行状态必须分离，自动恢复不能开启管理员手工停用的实体。

配置保存后对新请求生效；进行中请求使用开始时的配置快照，不被编辑或停用打断。旧请求的运行结果不得覆盖新配置的状态，尤其是编辑候选后的旧配置失败回报。

## 10. 错误响应

以下是统一错误契约；鉴权或请求体读取阶段的实现例外见第 17 节。

- 网关自身错误和经过转换的上游错误始终使用客户端入站协议的标准错误结构。
- 错误必须包含网关 `request_id`。
- 流式提交前保留合适的 HTTP 状态码；提交后只能发送客户端协议允许的错误事件并关闭连接。
- 上游原始状态、响应头和正文保存在 attempt 中，不直接把错误协议返回给客户端。
- 禁止吞错、返回默认假响应或静默切换到未配置模型。

## 11. 使用记录与日志

### 11.1 记录模型

一个使用记录代表一个入站请求；每一次上游密钥/候选尝试保存为其子 attempt。

发生协议转换时必须保存四阶段载荷：

1. 客户端原始请求；
2. 转换后的上游请求；
3. 上游原始响应；
4. 转换后的客户端响应。

为重建调用过程，四阶段记录要求保存状态行、完整请求/响应头和正文。SSE 保存原始事件序列，但不要求保存每个 chunk 的独立时间戳；当前保存形式见第 17 节。

用户明确要求：已授权 AI 请求中的入站密钥、上游密钥、Cookie 和其他凭据也按原文写入日志，SQLite 全部明文，不做字段加密或 SQLCipher。管理网页默认遮罩敏感头，点击后可以查看。遮罩只影响界面展示，不改变存储或管理员 API 的明文契约。

这是为私有实例排查和审计接受的风险：SQLite、快照或载荷下载泄露等同于其中的提示词、源代码和凭据泄露。压缩不构成加密；不要擅自将明文查看能力改成脱敏 API。

无效或缺失访问密钥的请求不保存完整正文和凭据，只记录精简安全事件：时间、IP、User-Agent、端点和失败原因，防止未授权访问者灌满数据库。

进程崩溃或被终止时遗留的 `in_progress` 请求与 attempt 在下次启动时统一标记为 `failed`，不会永久停留在进行中状态。

### 11.2 元数据

- 请求 ID 和状态；
- 访问密钥；
- 虚拟模型和真实模型；
- 供应商和上游密钥；
- 入站端点、入站协议、上游端点、上游协议；
- 客户端推理强度和实际推理强度；
- request attempt 数量与最终命中项；
- 请求时间；
- User-Agent；
- 客户端 IP；
- 客户端断开、网关错误和上游错误原因。

### 11.3 Token 口径

保存上游原始 usage JSON，并尽可能标准化为：

- 非缓存输入 Token；
- 缓存读取 Token；
- 缓存写入 Token；
- 输出 Token；
- 其中推理输出 Token；
- 总 Token。

单条 request / attempt 中，上游没有返回的 Token 指标保存为空值，不补 0，也不使用本地 tokenizer 估算；缺少总量时可以从真实回包的已知分量求和。客户端协议编码按目标规范补 0，与日志口径区分；统计汇总只累计已有指标，显示合计 0 不表示每条请求都报告了 0。原始流式 usage 的保存形式见第 17 节。

Chat 流式入口声明支持 usage 时，网关可对上游强制启用 `stream_options.include_usage`。客户端没有请求 usage 时，额外 usage 块只写日志、不转发。

### 11.4 延迟口径

- 总耗时：从网关完整收到入站请求到最后一个响应字节成功写出；客户端断开时记到检测到断开。
- 首内容延迟：从完整收到入站请求到首次向客户端写出有语义的文本或工具调用增量。响应头、心跳和 created/start 元事件不计入。
- attempt 另保存连接、首响应字节、首内容和完成时间，便于区分网络、上游排队和生成延迟。

### 11.5 载荷生命周期

默认保留完整载荷；管理员配置保留期后，过期已结束请求清空正文、头部和错误详情，保留结构化请求与 attempt 元数据和 usage，且明确标记载荷已清理。过期精简安全事件可以删除，进行中的请求不能被清理。参数与运行方式见 [运行与开发](operations.md#运行参数)。

进程中断遗留记录在启动时收尾，使其可以进入保留期清理和统计。按时间范围手工删除及 JSONL 导出属于第 14 节冻结能力。

## 12. 管理后台

技术栈：React、TypeScript、Vite、Ant Design、Tailwind CSS。

- Ant Design 负责表单、表格、弹窗、分页、通知和主题 Token。
- Tailwind 只负责页面布局、间距和少量定制展示，不覆盖 Ant Design 内部样式。
- 简体中文界面，协议名、JSON 字段和错误码保留英文。
- 桌面优先，提供基础平板响应式；不把复杂编辑流程适配到手机。
- 支持浅色、深色跟随系统和手动切换。
- 视觉方向为工业控制台式的克制精密：突出协议流向、状态和时间，不使用通用紫色渐变 AI 仪表盘风格。

### 12.1 登录

- 单管理员密码登录。
- 会话 Cookie 使用 HttpOnly，CSRF Cookie 供前端读取；两者均使用 Secure、SameSite Strict，并对管理写操作校验 CSRF。
- 会话 24 小时无操作失效，最长 7 天。
- 修改或重置密码后撤销全部现有会话。
- 按可信客户端 IP 计算，15 分钟内最多 5 次失败；成功登录清零，限速状态只存内存。

空数据库首次启动必须通过环境变量或命令行参数提供初始管理员密码，应用只保存密码哈希。忘记密码时停服执行 `model-confluence admin reset-password`，直接更新指定 SQLite 并撤销全部会话。不实现邮件或网页找回。

### 12.2 导航模块

1. 性能监控；
2. 使用记录；
3. 用量统计；
4. 上游健康；
5. 访问密钥；
6. 供应商；
7. 模型路由。

性能监控页按日期范围展示请求数、成功率、首内容与总耗时 P95、状态分布和异常与慢请求列表。用量统计页按日期和模型聚合 Token 用量与缓存命中分布，不做金额估算。上游健康页展示密钥池运行状态、候选近期失败和无可用路由的模型。

精简安全事件不增加用户/审计管理模块；独立查看视图的范围见第 14 节。

### 12.3 使用记录页

列表按时间倒序，使用服务端分页与筛选；当前提供时间范围、请求 ID 和访问密钥条件，并在 URL 保存查询状态。前端查询缓存必须包含所有服务端查询条件，避免换条件后复用错误结果。其他结构化筛选属于第 14 节冻结能力。

不做跨记录正文全文搜索。详情页内可以查找当前 JSON/SSE 文本。

请求详情包含：

- 请求摘要和状态；
- attempt 时间线；
- 四阶段载荷查看器；
- JSON 格式化与原文切换；
- SSE 事件查看；
- 复制与下载；
- Token 和延迟明细；
- 原始错误；
- 凭据默认遮罩与手动显示。

### 12.4 配置页

- 访问密钥支持创建、停用、过期、归档和最后使用时间查看。
- 供应商支持完整 URL、鉴权方式、静态头、额度错误码、结构化密钥池和状态编辑。
- 模型路由支持虚拟模型、候选顺序、真实模型、协议入口顺序和能力编辑。
- 模型路由支持测试虚拟模型连通性；测试使用真实路由、转换、密钥池与日志流程，不保证逐一覆盖全部候选。
- 被历史记录引用的配置需要保留关联，通过归档退出使用；无关联引用的配置才允许物理删除。仍被模型路由使用的供应商或协议端点不得删除。历史日志保存名称快照。

## 13. 配置、安全与运行

- 配置项、默认值和参数校验以 [配置定义](../internal/config/config.go) 为准；用户操作说明集中在运行与开发文档，不在本节重复数值表。
- 上游连接、响应头等待和读取空闲超时分别控制，不设置生成请求总时长上限，以适应长时间生成。请求体有可配置上限，超过时拒绝；响应流不设应用层总大小上限。
- 管理后台与管理 API 同源，不启用 CORS。
- SQLite 使用 WAL，所有时间以 UTC 保存，界面按浏览器时区显示。
- 数据库迁移嵌入二进制并在启动时以事务执行；schema 变化必须兼顾新建与已有数据库。
- 配置和日志写入失败时应明确失败：无法在调用上游前建立 request / attempt 记录就拒绝，不允许产生已知的无日志调用。调用后的持久化收尾差距见第 17 节。
- 客户端断开、上游取消和进程退出要传播 Go context 取消；当前进程退出行为见第 17 节。
- 进程诊断使用标准库 `log/slog` 输出到标准输出/标准错误，不另建应用日志文件。业务载荷保存在 SQLite，不写入普通运行日志。

## 14. 冻结能力与非目标

以下规划尚未实现，且不属于默认开发范围；保留它们是为了说明边界，不是待 Agent 自动完成的任务。扩展需由用户明确要求：

- 按时间范围手工删除使用记录及 attempts；
- 按筛选条件导出 JSONL，每行一个使用记录并内嵌 attempts、四阶段载荷和原始 usage；若未来启用，仍沿用载荷原文契约；
- 精简安全事件独立查看视图；
- 使用记录按状态、供应商、虚拟模型、真实模型、入站协议或上游协议的额外结构化筛选。已提供的条件见第 12.3 节。

长期非目标：

- 多用户、团队、租户、RBAC；
- 入站密钥模型权限、额度和速率限制；
- 计费、模型价格和金额估算；
- 时间序列趋势图和告警通知；
- CSV 导出；
- 自动同步供应商模型；
- 供应商插件体系；
- 配置导入导出、自动备份恢复；
- 横向扩容、外部数据库和高可用；
- 浏览器跨域模型调用；
- 后台实时尾随或取消进行中的模型请求；
- 完整移动端管理体验。

## 15. 性能目标

在常规个人服务器上，单实例目标为：

- 50 个并发流式请求；
- 短请求持续 20 RPS；
- 管理后台列表查询不加载完整载荷，详情按需读取；
- 网关转换不人为缓冲完整流式响应，只缓冲提交点前的起始元事件。

上述目标不包含上游模型延迟，也不承诺团队级或公网 SaaS 负载；这是设计容量目标，不能作为已经完成压测的声明。完整日志仍需保存流式载荷，因此「不缓冲完整响应再发送」不代表内存消耗与响应长度无关。

## 16. 核心验收目标

以下用于评估相关能力是否达到设计目标，不是每个任务的固定检查表，也不是现有测试覆盖率或真实客户端集成结果的声明。按变更语义选择受影响的场景；测试依据见 [协议测试](../internal/protocol/request_test.go)、[流式测试](../internal/protocol/stream_test.go)、[网关测试](../internal/gateway/handler_test.go) 和 store 相关测试。

### 16.1 构建与启动

- 前端构建后可生成一个包含管理后台的 Go 可执行文件；运行不依赖 Node.js。
- 空数据目录可初始化 SQLite 和管理员；再次启动不重复初始化。
- Linux 和 Windows 目标可以使用同一套源码构建。

### 16.2 管理闭环

- 管理员能够登录、修改密码和退出。
- 能创建访问密钥、供应商、多个上游密钥、虚拟模型及候选协议能力。
- 配置保存后，新请求无需重启即可使用。

### 16.3 API 与转换

- 9 个协议组合分别通过至少一个非流式文本场景和一个 SSE 文本场景。
- 6 个跨协议方向分别通过多轮工具调用；至少一个场景包含两个并行工具调用。
- Codex 通过 `/v1/responses` 转到 Chat Completions 候选，连续完成至少 3 轮客户端工具调用。
- Claude Code 通过 `/v1/messages` 转到 Chat Completions 或 Responses 候选，连续完成至少 3 轮客户端工具调用。
- 不支持字段、状态会话、未支持的多模态字段和思考块在上游调用前返回明确错误；URL、data URL 和 base64 图片输入除外。
- 同协议未知字段可以透传，跨协议未知非空字段被拒绝。

“支持 Codex/Claude Code”表示配置网关地址、访问密钥、虚拟模型和少量明确兼容设置后，文本、图片输入、流式和工具核心代理循环可用；不承诺主动开启音频、视频、文件、跨协议思考块、状态会话或托管工具后仍然可用。

### 16.4 路由与故障

- 密钥池能在 401、明确额度耗尽和普通 429 下按规则切换。
- 403 不会永久禁用密钥。
- 候选能在连接失败、超时、5xx、模型不存在和提交点前解析失败时切换。
- 流式提交后不会拼接第二个上游响应。
- 客户端断开会取消上游并保存 partial/cancelled 记录。

### 16.5 日志与后台

- 每个已授权请求能查看完整 request、attempt 和四阶段载荷。
- Token 缺失显示为空，不显示伪造的 0 或估算值。
- 首内容延迟不被 created/start 元事件提前触发。
- 请求详情与已开放的服务端筛选正确工作；冻结能力见第 14 节。
- 未授权请求只产生精简安全事件。

| 客户端流式 usage（11.3） | 上游支持时会启用 Chat include_usage，但代理与转换编码没有按客户端是否请求 usage 统一过滤，额外指标可能直接发送给客户端。仅写日志的要求仍是设计目标。 | [网关代理](../internal/gateway/handler.go)、[流式编码](../internal/protocol/stream_encode.go) |
| 可信代理与退出（2、13） | 客户端 IP 解析只处理可信对端的 X-Forwarded-For，尚未支持 Forwarded。进程信号触发有期限的 HTTP Shutdown，但未把进程信号 context 直接作为所有请求 context 的取消源；不能声称信号到来立即取消所有上游。 | [IP 解析](../internal/httpx/httpx.go)、[程序入口](../cmd/model-confluence/main.go) |

供应商兼容知识应落到协议字段和测试中。以已有火山方舟接入观察为例：Messages 的 `cache_creation_input_tokens` 按该协议映射为缓存写入；Chat / Responses 不能凭其他协议的字段补数。未来供应商改变回包时，以真实样本和对应协议的 usage 定义重新评估，不按供应商名称猜测指标。保留明文 reasoning summary 的转换能力，也不对只含 encrypted_content 的回包承诺等价转换。
